<objective>
Upgrade Supabase packages and fix the SSR session bleed by re-enabling the middleware cookie writeback with the dual cookie-write pattern and cache-control headers.

Purpose: This is the critical security fix for Phase 1. The current middleware has `setAll` intentionally disabled (no-op), which means refreshed tokens are never written back to the browser. This causes stale sessions and potential cross-user contamination under SSR. The upgrade to @supabase/ssr v0.10.2 also introduces cache-control headers in the `setAll` callback that must be applied to prevent CDN/CloudFront from caching authenticated responses.

Output: Working middleware with dual cookie-write, cache-control headers, redirect contract with reason+next params, and upgraded Supabase packages.
</objective>

**Replace the entire content of `src/utils/supabase/middleware.ts` with:**

```typescript
import { createServerClient } from "@supabase/ssr";
import { NextResponse, type NextRequest } from "next/server";

const supabaseUrl = process.env.NEXT_PUBLIC_SUPABASE_URL!;
const supabaseKey =
  process.env.NEXT_PUBLIC_SUPABASE_PUBLISHABLE_DEFAULT_KEY ??
  process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!;

export async function updateSession(request: NextRequest) {
  let supabaseResponse = NextResponse.next({ request });

  const supabase = createServerClient(supabaseUrl, supabaseKey, {
    cookies: {
      getAll() {
        return request.cookies.getAll();
      },
      setAll(cookiesToSet, headers) {
        // Write to request so downstream Server Components see the refreshed token (D-01, D-04)
        cookiesToSet.forEach(({ name, value }) =>
          request.cookies.set(name, value)
        );
        // Recreate response to pick up modified request headers
        supabaseResponse = NextResponse.next({ request });
        // Write to response so browser receives the refreshed token
        cookiesToSet.forEach(({ name, value, options }) =>
          supabaseResponse.cookies.set(name, value, options)
        );
        // Apply cache-control headers to prevent CDN caching of authenticated responses (v0.10.2)
        if (headers) {
          Object.entries(headers).forEach(([key, value]) =>
            supabaseResponse.headers.set(key, value)
          );
        }
      },
    },
  });

  // IMPORTANT: Do not add logic between createServerClient and getClaims.
  const { data, error } = await supabase.auth.getClaims();
  const isAuthenticated = Boolean(data?.claims?.sub);
  const path = request.nextUrl.pathname;

  if (error) {
    // If already on an auth page, allow the request to proceed so the user can log in
    if (path.startsWith("/auth")) {
      return supabaseResponse;
    }

    // Only log actual errors, not "session missing" which is expected for unauthenticated users
    if (!error.message.includes("Auth session missing")) {
      console.error("Auth error in middleware:", error);
    }

    // D-03, D-05, D-06: Redirect to login with reason and preserve intended destination
    const loginUrl = request.nextUrl.clone();
    loginUrl.pathname = "/auth/login";
    loginUrl.searchParams.set("reason", "session_expired");
    loginUrl.searchParams.set("next", request.nextUrl.pathname);
    return NextResponse.redirect(loginUrl);
  }

  if (!isAuthenticated && path.startsWith("/dashboard")) {
    // D-03, D-05, D-06: No valid user on protected route -- redirect with context
    const loginUrl = request.nextUrl.clone();
    loginUrl.pathname = "/auth/login";
    loginUrl.searchParams.set("reason", "session_expired");
    loginUrl.searchParams.set("next", request.nextUrl.pathname);
    return NextResponse.redirect(loginUrl);
  }

  if (isAuthenticated && path.startsWith("/auth")) {
    const url = request.nextUrl.clone();
    url.pathname = "/dashboard";
    return NextResponse.redirect(url);
  }

  return supabaseResponse;
}
```

**Update `src/utils/supabase/server.ts`** to be compatible with v0.10.2 `setAll` signature. The server client's `setAll` can safely ignore the `headers` parameter since middleware owns cache header application. Add a try/catch around cookie writes for Server Component safety:

```typescript
import { createServerClient } from "@supabase/ssr";
import { cookies } from "next/headers";

type CreateClientOptions = {
  allowCookieWrite?: boolean;
};

const supabaseUrl = process.env.NEXT_PUBLIC_SUPABASE_URL!;
const supabaseKey =
  process.env.NEXT_PUBLIC_SUPABASE_PUBLISHABLE_DEFAULT_KEY ??
  process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!;

export async function createClient(options: CreateClientOptions = {}) {
  const cookieStore = await cookies();
  const allowCookieWrite = options.allowCookieWrite === true;

  return createServerClient(supabaseUrl, supabaseKey, {
    cookies: {
      getAll() {
        return cookieStore.getAll();
      },
      setAll(cookiesToSet) {
        // Server Components cannot reliably set cookies.
        // Middleware handles cookie writeback and cache headers.
        // Only the OAuth callback should use allowCookieWrite: true.
        if (!allowCookieWrite) return;
        try {
          cookiesToSet.forEach(({ name, value, options }) =>
            cookieStore.set(name, value, options)
          );
        } catch {
          // Called from a Server Component -- cookies are read-only.
        }
      },
    },
  });
}
```

4. **server.ts**: Added try/catch around cookie writes for Server Component safety

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser -> Middleware | Cookies from untrusted client, validated by Supabase getClaims() |
| Middleware -> Downstream SSR | Refreshed cookies forwarded via request.cookies.set for server components |
| Middleware -> Browser | Refreshed cookies written to response for browser storage |
| Middleware -> CDN (CloudFront) | Cache-control headers prevent CDN from caching authenticated responses |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-1-01 | Information Disclosure | src/utils/supabase/middleware.ts | mitigate | Re-enable `setAll` with dual cookie-write pattern: `request.cookies.set` + `supabaseResponse.cookies.set`. This is the direct fix for the SSR session bleed. |
| T-1-02 | Information Disclosure | CDN caching Set-Cookie headers | mitigate | Apply `headers` from `setAll` second argument to response: `Cache-Control: private, no-cache, no-store, must-revalidate, max-age=0`, `Expires: 0`, `Pragma: no-cache`. Provided by @supabase/ssr v0.10.2. |
